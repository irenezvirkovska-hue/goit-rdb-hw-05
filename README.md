# goit-rdb-hw-05

Домашнє завдання №5: побудова аналітичних ознак за допомогою CTE, рекурсивних запитів і матеріалізованих представлень у PostgreSQL.

## Дані та середовище

- **Дані:** Olist Brazilian E-Commerce Dataset, завантажений через KaggleHub.
- **Середовище:** Google Colab, Python, PostgreSQL через `pgserver`.
- **Робота з даними та SQL:** pandas і SQLAlchemy.
- **Шари даних:** `raw` для початкового завантаження CSV та `typed` для таблиць із відповідними типами даних.

Для розрахунків використано дані про клієнтів, замовлення, позиції замовлень і товари.

## Виконана робота

### 1. Підготовка даних

Завантажено датасет, запущено PostgreSQL у Colab і створено raw та typed шари для подальших SQL-запитів.

### 2. CTE-chain для розрахунку ознак

Побудовано послідовність CTE з результатом на рівні `customer_id`:

| Ознака | Опис |
|---|---|
| RFM | `recency_days` — давність останнього замовлення; `frequency` — кількість замовлень; `monetary` — їхня загальна вартість |
| Cohort | Дата першого замовлення та квартал, до якого вона належить |
| Rolling AOV | Середня вартість замовлення у 30-денному вікні; у фінальному результаті — значення для останнього замовлення |
| Cancellation rate | Частка замовлень зі статусом `canceled` |
| Preferred category | Категорія з найбільшою сумарною вартістю покупок та відповідна сума |

Вартість замовлення включає ціну товарів і доставку. Опорна дата для RFM — день після максимальної дати покупки в датасеті. Розрахунки виконуються за `customer_id`, а не за `customer_unique_id`.

### 3. Recursive CTE для referral chain

Створено навчальну таблицю `hw5_referrals` із ланцюжком із 10 клієнтів. Це штучні зв’язки для демонстрації рекурсії.

Запит `WITH RECURSIVE` містить початкову та рекурсивну частини, визначає глибину `depth` і шлях проходження. Повторне відвідування клієнта блокується перевіркою `path_ids`; максимальна глибина обмежена 50 рівнями.

### 4. Materialized View

Повний результат CTE-chain збережено в `mv_olist_customer_features`. Створено `UNIQUE INDEX` за `customer_id` і виконано оновлення:

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_olist_customer_features;
```

Матеріалізоване представлення дозволяє читати готові ознаки без їх повторного обчислення. Актуальність результату залежить від часу останнього оновлення.

### 5. Аналіз виконання

За допомогою `EXPLAIN (ANALYZE, BUFFERS)` досліджено переобчислення RFM через CTE та пошук клієнта в матеріалізованому представленні. Розглянуто агрегації, сортування й використання індексу. Ці запити мають різний обсяг роботи, тому їхній час не є прямим порівнянням однакових операцій.

У Reflection описано вартість обчислень, вибір між VIEW і Materialized View, оновлення даних та захист рекурсії від циклів.

## Як запустити

1. Відкрити notebook домашнього завдання в Google Colab.
2. Підключити середовище виконання та запустити комірки встановлення залежностей.
3. Виконати завантаження Olist через KaggleHub і запуск PostgreSQL через `pgserver`.
4. Послідовно виконати комірки створення та заповнення raw і typed шарів.
5. Запустити CTE-chain, referral chain, створення Materialized View, унікального індексу та `REFRESH CONCURRENTLY`.
6. Виконати комірки `EXPLAIN (ANALYZE, BUFFERS)` і переглянути результати.
7. Перед здачею перезапустити середовище та виконати всі комірки послідовно (**Restart & Run All**). Зберегти notebook із результатами виконання.

Після видалення тимчасового середовища Colab дані та локальну базу потрібно створити повторно, запустивши notebook з початку.
